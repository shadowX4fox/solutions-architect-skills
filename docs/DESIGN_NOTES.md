# Design notes

The measurements, probes and history behind rules that `CLAUDE.md` states in their current form.
Moved here verbatim (8.71.0) so `CLAUDE.md`, which every session in this repository loads, carries the
rules and this file carries the evidence. Read a section when a rule is questioned or a probe is about
to be retried.

## Judge

`scripts/judge.js` — **the one judge** (2026-09-21; the `claude` provider from 8.70.0 until 8.120.0, when Cloudflare's Clef replaced it (the same System One protocol as Jev, so the typesafe provider with another endpoint, token and model, and an optional AI Gateway header) — Claude through the official SDK, `@anthropic-ai/sdk` an optional dependency loaded only for this engine, one structured-output answer per batch validated in code, the same content cache, `fallbacks: "default"` on a declined request, `SA_JUDGE_CLAUDE_MODEL` (claude-opus-5) and `SA_JUDGE_EFFORT` (medium); its probabilities are stated, not calibrated like Jev's, so a site's bands are verified before trusted): every semantic verdict a script needs over candidates code already found — which component a prose name refers to, whether a mitigation is in place, whether an ADR changed in substance, whether a passage asserts a retired claim — is one typed question per item through this module, never a private lexicon or substring test. A spec (`id`, `type` `noul | choice | score`, `question`, `criteria`, `hi` / `lo`) and items (`id`, `state`, per-item `options` for a choice) go in; one normalized answer per item comes out, each stamped `by:` the provider that gave it. The providers, the only thing that changes between engines (the `heuristic` provider — the caller's own scoring function — existed until 8.119.0, when it was removed: an unanswered item is undecided and reported, never ranked as an answer): `agent` (a worksheet under `.cache/sa-skills/judge/` the session judges, answers applied on a second call, an unanswered item reported and never defaulted), `typesafe` (Jev over the TypeSafe System One API, batched by chunk, retried on 429 / 5xx / 529, every answer **cached by a hash of model + question + criteria + state** so a re-run over unchanged items makes no request and reproduces). Engine chosen once per machine: the caller's option, else `SA_JUDGE`, else **`agent`** (8.71.0 — every caller handles `pending`: an unanswered worksheet leaves its items undecided in that run and names the worksheet — through 8.118.x the site's own heuristic stood in; `/setup` Step 9 writes `env.SA_JUDGE = "agent"` into the project settings when no scope sets it, and leaves any set value alone); `SA_JUDGE_MODEL` overrides `jev-latest`; the key is `TYPESAFE_API_KEY`, in the shell profile **above any "not interactive" guard**, never in a versioned file. `verify` measures answers against fixtures and separates a Stage 1 miss (the item never reached the judge — fix the recall) from a judge miss. What never goes to the judge: counts, arithmetic, dates, thresholds — Stage 3 is code, and Jev is literal and weak on numbers (docs.typesafe.ai jaggedness). `scripts/setup-judge.ts` applies the `agent` default to the project settings when unset and reports the engine in force, the key (set or not, never the value, refused inside `.claude/settings.json`), the model, one probe item answered by the API, and the cache; `/setup` Step 9 runs it as a report. First consumer: `tools/claim-sweep/` (recall by block + policy in code, one Noul per block); on the reference project 134 blocks in 6 requests / 2.6 s, 13 of 13 fixtures at the claim's measured cut of 0.65, 0 false positives, 68 of 134 scores drifting up to 0.15 between two live runs with none crossing the cut. Second: the docs/05 edge direction in `analysis-prepare.js` (see *Analysis pipeline*). Third: **`scripts/resolve-name.js`, the one resolver for "which component does this prose name refer to"** — the containment rule the scripts carried inline (earliest name in the cell wins) finds the candidates (it was the heuristic provider until 8.119.0); a cell that is exactly one candidate's name is answered by code and never judged (Jev answered `none` at 0.05 for an exact "Servicio de Riesgo y Fraude" on the reference — a two-option Choice distracted by the row's context); the judge sees a cell with a qualifier, two names, a tie or no name: one Choice over the containment hits (or every file-backed component when nothing is contained) plus `none`, each option described by level, system, internal name and the 8.64.0 tagline, and one Noul per further hit ("does the cell also name it as an endpoint, not as a via or a qualifier"). A zero-hit cell resolves only at high confidence ("AppDome" came back as the mobile app at 0.54 — a self-edge contract had it resolved). `handoff-prepare.js` is the first caller (`--judge`, `--judge-answers`, `--judge-also-answers`, `--verify`): the contract count is unchanged — the contract goes to the first name — and `endpoint_review` (the CONTEXT_RESULT block and the stderr review) carries every second name and every mid-band pick, so "Aplicación Tienda Móvil y Base Local de Pedidos" no longer collapses in silence; 12 of 12 fixtures on both engines, and Jev's review is three lines to the rule's five because its Nouls reject the substring hits (`Cache de Pedidos` inside `Escritor del Cache de Pedidos`, `APIM`, `Auth0`). **A cell that is exactly a fact's full name is code's, whatever shorter names it contains** ("Captura CDC del Sistema de Pedidos" contains "Sistema de Pedidos" — judged at 0.37 until the rule keyed on the whole cell). Fourth: `analysis-prepare.js` `canon` — every name the graph uses (docs/05 cells, the descriptors' Depends on / Consumed by link texts) goes through the resolver in one batch over the **whole ledger, systems included** (offered only the containers, the judge picked `Base Despachos Nacionales` at 0.32 for the L1 `Motor de Despachos Nacionales`); an unresolved name still enters the graph as its raw string — the document's word — and the manifest's `judge.names` plus the summary's `names:` line report it, with the second names and mid-band picks under `names to confirm`; `--judge-names` closes the agent loop. **Not every resolver site is a judgement**: the dossier's `nodesLoose` (which containers a finding lights on the stage) was the fifth candidate and is a **column rule** now — the row is read through `mentionCandidates` without its mitigation and recommendation cells (`PASSING` in `dossier.js`), which on the reference unlit exactly the 5 mentions that sat only under *Bulkhead Present*, *Current Mitigation* and *Recommended Mitigation*; a first cut asked Jev per (finding, component) and it dropped members of a Blast Radius fan-out at random (kept `Cache de Pedidos`, dropped `Escritor del Cache` from the same cell), because a blast radius is about every component it reaches. `mentions()` stays in the module for the sites where "is the text about it" is real. Sixth: **the scene builder** (`scene-from-docs.js`, `--judge`) — every name its edge and phase passes will need (docs/05 cells, Communication endpoints, chain participants) is collected in a pre-pass and resolved in one batch before either pass runs, with two companion questions the module gained for it: `COVERS` (which containers a plural such as "Tópicos CDC" covers — one Noul per candidate the prefix rule found) and `RELATION` (whether two containers named in one Description act in `parallel` or in `sequence`, the connector-word rule as heuristic; `sequence` is what becomes an inner edge). Two leaks the live run exposed, both closed in code: **a cell never means the other endpoint of its own row** — offered the whole ledger for "AppDome", Jev picked the mobile app at 0.76 and the row self-edged, so every caller passes `exclude` (the other end's exact name) and the resolver drops it from the pool; and the docs/05 splitter cut "Servicio de Riesgo y Fraude" on its own "y" — a cell that is exactly a node's name is one part. A name the judge half-recognized (`possibly X`, below the floor) is neither a container nor an actor: it is reported, so a typo stops becoming a person. With those, the reference scene is **byte-identical on both engines** (34 nodes, 3 actors, 50 edges, the same 2 synthesized hops) and Jev raised no review line over 3 names and 15 description pairs — the rule was right on that corpus, and now it is checked rather than assumed. Then the five remaining judgement sites, each `--judge`-able and each keeping its old rule as the heuristic provider (`resolveNames` takes `heuristic(cell, pool)` for that): `security-posture.js` binds each G-row to an inventory store (the three-way fuzzy rule was the heuristic; identical 139 checks on both engines on the reference, 2 rows to confirm either way); `render-analysis.js` `applyCrossRefs` joins Blast Radius rows to SPOF findings (exact by code; a drifted label by the judge over the SPOF labels, printed as `SPOF cross-references bound by …`); `sa-export-assemble.js` resolves a layer-table name that is not exactly a component's before falling through to "it must be a system" (`report.layer_names_judged`); `handoff-prepare.js` `nodeOf` binds every container-diagram node label to a component (`report.panels.judged`); `flow-check.js` compares `phase-absent` participants by **canonical** name — every display name resolved once, `participant-alias` warnings name the reading ("Azure APIM" → `APIM`), so an aliased lifeline no longer fires a false finding. **Not moved, on purpose**: `component-facts.ts` `normName` (exact after accent strip — a defensible rule inside the ledger every consumer reads), `kit-check.js` (lexical by design), `handoff-prepare.js` `rowsWith` (a warning-only containment cross-check), `flow-compose.js` (its display-name union is the authored lifeline text and changing it rewrites docs/04). **Then the two contract-level questions** (2026-09-21): `findings.js` gains `judgeMitigations(entries, opts)` — `enrich` stays synchronous (it is the contract every gate runs) and this async pass re-reads each mitigation cell afterwards for the consumers that rank by residual (the dossier, `--judge`): one Noul per cell, *"does the `column` cell state that the mitigation that column asks for exists now, in whole or in part"* — the meaning is the column's per lens (a bulkhead, a backpressure mechanism, an exit path, an implemented replacement, a STRIDE status), and the first cut that asked for "a control operating today" flipped every vendor exit path and every bare "Partial" to none, the model answering the question as written. A state changes only on a confident answer (≥ 0.75 present, ≤ 0.25 none); in between the lexicon's reading stays and the cell prints under *mitigations to confirm*. On the reference, 107 cells: the lexicon read "Sin respuesta la app arranca con los valores por defecto…" as none (its `sin` token) and the judge reads the fallback it describes at 0.96; two "Parcial — …" cells that describe an effect and no mechanism go to none; three sit within 0.03 of the cut and are reported, not changed. `catalog-diff.ts` gains `judgeCosmetic(diff, editionDir, projectRoot, opts)` — every `cosmetic` pair's removed and added lines (after `canon`, the smallest state that carries the change) go to one Noul, *"does the change alter what the record decides, why, or what follows, in substance"*; the heuristic keeps the pair cosmetic; a confident yes promotes it to `amended` with `changed_sections: ["(judged)"]` and `judged: { p, by }` and recounts the summary — the 6.14.4 blind case (headings the section finder does not recognise) is what it exists for, and `catalog-diff-cli.ts diff … [--judge <engine>]` prints the result under `judge`. **The principle gate's Layer 1.5** (`principle-check.js` `judgeFindings`, `--judge`; 2026-09-21): five of the sixteen `P-*` rules stand in for a judgement with a word list (`P-TRADEOFF-QUANT-01` cost nouns, `P-TYPE-MATRIX-01` concept phrases, `P-PLATITUDE-01`, `P-TRADEOFF-NEG-01`, `P-QA-CONFLATION-01`), all BLOCKING, and a false block costs a rewrite round. `check` stays synchronous and untouched; when it blocks, every BLOCKING finding of those five rules goes to the judge with the question the lexicon approximates (one request per rule, in parallel) and a confident answer against the lexicon **downgrades the finding to WARNING with the reading, never drops it**; the `results` row turns `WARN` when no finding of the rule still blocks; a lexicon PASS is never re-judged (Layer 2 reads the whole section). On the **8.30.0 control corpus** the lexicon blocks five findings — three Trade-offs "with no cost noun" (P7's name a larger local database, an unverified Couchbase skills gap and two read paths to maintain) and two META principles "missing the concept" (P1's Implementation opens with *Modelo de 6 capas META*) — and Jev downgraded all five at 0.95–0.97: the corpus that "failed six rules" failed a word list. **The traceability skill has a script** (`skills/architecture-traceability/scripts/traceability-prepare.js`, 2026-09-21; the skill had none — Steps 3–6 ran in session, 115 verdicts with no fixture and no Unknown): the use cases and their fields parsed in either language, the requirements by the Step 3 table, the evidence per requirement cut by the explorer over the **whole surface** (a first cut searched `docs/` only and ranked by the explorer's term count — the best excerpt was routinely a file's EXPLORER_HEADER comment, and the ADRs the gold report cites on every other row were never searched; Jev answered honestly on that evidence: 32 covered of 120), ranked by overlap + the Step 4 route + the project's own documents before its ADRs before the institutional catalog, header and heading-only excerpts dropped, a wide file cap so the SLO table of docs/08 is not lost behind thirty files that say "sesiones"; then one **Score per requirement whose three levels are Covered / Partial / Not Covered** (no threshold to fit) and one Noul per flow step for "pure UI navigation" (not traced). The heuristic ranks by term overlap **and the report says so**; a Partial's gap text is `[NOT DOCUMENTED …]`, never composed; `--json` hands the session every requirement with its candidates, score and confidence. Reference: Jev 72 / 47 / 1 of 120 in 5 s against the 2026-09-08 session's 91 / 14 / 10 of 115 (architecture 2.1.0, now 7.0.0) — the judge reads six excerpts, the session read the documents; the excerpts are what to improve and every row prints them. Tests: `skills/architecture-traceability/tests/traceability-prepare.test.ts`. **BIAN alignment has a shortlist script, and the verdict stays the session's** (`skills/architecture-bian-alignment/scripts/bian-prepare.js`, 2026-09-21): the corpus parsed by code (341 definitions, DOM / CAP joined from the registry), the initiative brief cut from the spec, one Noul per (use case, Service Domain) — 2 728 on the reference, 22 s, cached — a realizes / consumes Choice for the claimed, the Business Domain and Area statuses derived bottom-up from the registry; `--verify <reviewed BIAN_ALIGNMENT.md>` measures recall and precision at four cuts. The objectives and the constraints are pair units too, since the gold's Regulatory Compliance and Payee Management live there, not in a use case — those two the judge still never reaches, and they are the session's. `scripts/judge.js` gained `shared` state for it (sent once per request, part of every cache key). **The language audit of every judged site** (2026-09-21, later): the dilemma is a *mixed-language state*, not a Spanish corpus — every question and criteria is English by design and the state is in `doc_language`, and the sites that compare Spanish to Spanish (claim-sweep, edge direction, the resolver, mitigations, principles, prose, traceability, catalog diff) measured well; a control on claim-sweep with the same Spanish passages under an English question came out *worse* (12 of 13 at 0.65 against 13 of 13, one positive at 0.62), so the question's language is left as the author wrote it. The prose judge's criteria carry the rulebook's Spanish examples beside the English ones. **Two traps of this work, recorded so they are not repeated**: a `sed "${n}a…"` with an empty `$n` appends after *every* line (162 and 331 copies landed in two scripts; `grep -n` had returned nothing because a backtick in the pattern was eaten by the shell — use `grep -n -F`, and check `$n` is non-empty before `sed`); and a test that serves a fake API from its own process must spawn the script asynchronously (`Bun.spawn` + `await p.exited`), since `spawnSync` blocks the event loop the fake server needs. Tests: `scripts/judge.test.ts`, `scripts/setup-judge.test.ts`, `scripts/resolve-name.test.ts`.

## Compliance

**sa-compliance 2.4.0 (2026-10-03) — the same documents give the same verdicts.** The judge was already deterministic (answers cached by the exact text asked about); all run-to-run movement came from the reader writing that text. Two rules: the reader cites (a payload passage or a line range) and code copies the text; evidence is carried forward per requirement under a key over the requirement and its ranked passages, while every cited text is still in its file (a `not found` while the read set is unchanged). Measured on a copy of the reference project, judged by Jev: a carried run read nothing, its nine sheets byte-identical, 67 of 67 verdicts identical; two fresh citing runs agreed on 60 of 67 — readers worked line numbers out from a passage's start label and cited the wrong row — and on 63 of 67 once every payload line carried its file line number (1,687 lines checked against the files, none off); a one-line edit to the security section sent 8 of 67 requirements back to a reader.

**sa-compliance 2.7.0 (2026-10-07) — Haiku 5.5 readers.** Re-measured on the Spanish reference, nine judged contracts (67 rows), four arms reading the same payloads (Sonnet ×2, Haiku 5.5 ×2), evidence by code and one shared Clef cache so only the reader varied. Written verdicts (below 0.60 → Unknown): Sonnet-Sonnet 65/67, Haiku-Haiku 63/67, Sonnet-Haiku 64/67 in all four pairs. Sonnet's two runs moved two contracts (enterprise 7.1 / 5.7, security 8.6 / 7.1), Haiku's three (data-ai 4.3 / 5.7, platform 3.3 / 1.7, security 8.6 / 7.1); nearly every flip was a row the judge put at 0.52–0.58 — the 0.60 cut, not the reader. Haiku's one distinctive verdict (a FAIL at 0.94) cited a regional single point of failure the Sonnet readers missed. Haiku 5.5 readers took ~23 s (16–52) against Sonnet's ~10 s (6–43). The 2.3.0 result below was Haiku 4.5. Next lever, if any: the 0.60 cut itself, where both models flip.

**sa-compliance 2.3.0 (2026-10-03) — Sonnet readers.** With the payload readers on Haiku, two runs a day apart over unchanged documents moved three contracts by 1–3 points (platform 5.0 → 1.7): the judge put two quotes at 0.48 and 0.45 in one run and in the To Confirm band in the other. Two Sonnet runs over the same payloads, judged by Clef: 65 of 67 verdicts the same, 7 of 9 contract scores the same (the two differences: one integration row FAIL / PASS, one process row Unknown / PASS); Sonnet against that Haiku run agreed on 59–61. Each Sonnet reader finished in 20–30 s, Haiku in 60–110 s.

**sa-compliance 2.2.0 (2026-10-02) — a fingerprint per contract.** 2.0 fingerprinted the whole corpus because a reader could quote any file; with 2.1.0 a contract reads only its domain's read set (payload, index sections, recall windows), so the contract is a function of that set plus the facts code reads for it (applicability, ADR claims, confirmations, TDRs and the month for development). Measured on a copy of the reference project: an edit to the security section re-runs 4 of 10 contracts, one to the system overview 3; a judge switch re-runs all 10. The check computes the ten fingerprints in under 50 ms.

**sa-compliance 2.1.0 (2026-10-02) — reader payloads.** Measured on a 2.0.1 run of a Spanish reference project: the ten readers spent 121 turns at 121K context per turn (≈ $3.46), loading their agent file and config and then exploring the corpus — one top-level document read nine times across the run. Cut by code, the payload (requirements + criteria, six ranked passages each, a section index) gave 78 turns at 85K (≈ $1.83) and 60 of 67 verdicts unchanged at first. The losses traced to two reader habits, both fixed as rules: taking the first passage when a later one answers, and writing "not found" or an inference without opening a section. Comparing the evidence sheets showed the baseline itself carried three Compliant verdicts with no statement behind them (a fabricated "no AI is used", a classification "implied", fields framed as personal data) — the payload readers, told to quote statements and never absences, leave those Unknown / To Confirm. The development candidates were cut at 240 characters, which dropped the clause that overrode a version floor and let the reader list a version the system does not run; each hit now carries ±180 characters around it.

**sa-compliance 2.0.0 (2026-10-02) — one layer.** Measured before the change: the 154 template requirements were one organization's standards, each typically several controls, many specific to one kind of design, written against guidelines the plugin cannot read; on the reference project 79 were Non-Compliant, and no judge could be held to a requirement whose evidence was a whole guideline. The rubric questions (67 after 1.1.x) had already been rebuilt to one control each and admitted by three judges, so the two layers were collapsed: the requirement IS the question. What the measurements settled, not to re-litigate: NA is code's (`applies_when`), never the judge's; a question enters only when typesafe, clef and agent each answer its fixtures as labelled at ≥ 0.75 (one item per request — batching moved answers); the blind agent pass uses opaque fixture ids in a shuffled order (fixture order leaked labels); the development contract is arithmetic over looked-up dates, never a model verdict; a verdict below 0.25 is Unknown in the contract. The first live run on a 2.0 corpus (recall only, no reader): security 5C / 1NC / 1U, SRE 1C / 2NC / 7U — the reader's quotes, not the recall windows, are what lift an SRE contract out of Unknown, as the 86% / 51% measurement of 1.0 predicted.

10 compliance contracts (Contratos de Adherencia) in `compliance-docs/`. **The judge is required and there is no lexicon engine** (8.66.0; 8.70.0 admits `claude`): `utils/judge-gate.ts` refuses the run at `compliance-prepare-cli.ts` — before a template is expanded or an agent dispatched — unless `SA_JUDGE` is unset / `agent` (the default since 8.71.0 — the session: Steps 3.3b and 3.6 write one worksheet per domain / contract and exit 10, the session answers each — `{"worksheet": <fingerprint>, "answers": …}`, a stated confidence lands mid-band — and the step re-runs with `--answers`; answers for changed items are refused), `typesafe` (with `TYPESAFE_API_KEY`) or `claude` (with the Anthropic SDK and a Claude credential), and when the probe item goes unanswered (`--no-probe` skips the probe); the gate's engine answers every judged call of the run (`fills-audit`, `rubric-judge`), and a sub-item the claude engine leaves unanswered keeps its status and is reported; every other judged site in the plugin keeps its lexicon as the default engine, this one does not, because a status guessed by a word list reads as evidence and is not. **The status is the judge's** (Step 3.6, `utils/fills-audit-cli.ts`): the generator finds the fact and writes it, one Choice per sub-item over the four statuses decides which one it supports — with the requirement's own text in the state — and three bands apply it (≥ 0.75 replaces and prints, ≤ 0.25 keeps, in between prints under *statuses to confirm* and changes nothing); structural defects are code's and never judged (a status with nothing recorded, `Compliant` cited to `Not documented`, a schema item with no fill). **Every sub-item records its fact, `Non-Compliant` included** (8.66.6): the exemption rested on a silent corpus having nothing to state, but the silence is the finding, and `hasValue` shares the scorer's `NOT_DOCUMENTED` list so the status cannot be written into the value slot instead — 153 of the reference portfolio's 692 sub-items fail it today, while development passes clean, so `compliance-generator.md` moved with the rule. Since 8.66.5 the two that **depend on a status** are read off the status the run leaves on disk, not the one the generator wrote, because the judge moves a status afterwards: the first judged run exited 1 on five defects that were the five sub-items it had moved `Unknown` → `Non-Compliant`, a status neither rule covers. A bracket inside an inline code span is quoted text and not an unfilled slot (`render-contract.ts`), since the External Validation Summary quotes architecture passages verbatim and one carried the corpus's own `[NOT DOCUMENTED]` marker. Measured on the reference project: 88% agreement with the generator's own statuses over 85 sub-items in 1.5 s, the criteria wording worth four of those points, and one real defect found. Contracts the pass changed are re-rendered before scoring. **The rubric is judged, the agent reads** (Step 3.3b, `utils/rubric-judge-cli.ts` + `utils/recall.ts` + `recall/lexicon.json`): the `domain-validator` agent no longer returns verdicts — it returns an `EVIDENCE_SHEET` of quotes with their files, pinned to Haiku, and one Choice per rubric item **whose options are the item's own `criteria` from `agents/configs/<domain>.json`** writes the `VALIDATION_RESULT` block the generator already parses. Measured over all 132 rubric items of the nine domains: **86%** agreement with the agent run when a reader feeds the judge, **51%** when it rules over code-cut passages alone — so recall supplements a reader and never replaces one, because a rubric verdict often rests on evidence assembled across sections. `recall.ts` is the bilingual Stage 1 (the lexicon crosses EN↔ES, since 65 of the 131 config patterns match nothing in a Spanish corpus; a stem is weighted by inverse document frequency, and the passage sent is the **window around the hit with its table header**, never the head of a 5 KB section — that one change moved cloud from 47% to 60%). Three probes that did not survive measurement, recorded so they are not retried: the judge routing a sub-item to its document from headings alone (37%), the judge selecting the passage inside the right document (`none` for 20 of 26), and counting distinct stems without IDF. **The generator's payload is the cut, not the bundle** (8.66.0): `compliance-prepare-cli.ts` writes `.cache/sa-skills/candidates/<type>.md` — per sub-item the four windows most likely to hold its fact (label + requirement text through the same recall), the requirement text per code, the `source_hint` per sub-item and an index of the domain's documents with what each holds and its sections — and the generator reads **that** plus the schema, never `corpus/<type>.md` again (264 KB → 84 KB on the reference cloud contract, 28 of 28 sub-items with candidates).
