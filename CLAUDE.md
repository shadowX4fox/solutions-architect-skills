**Edits are surgical** (8.32.2, from Anthropic's Fable 5.1 prompting guide § *Prefer targeted edits over whole-file rewrites*): when it will not affect the end result, edit a file at the lines that change rather than rewrite it — a `Write` of a whole document is for a file that does not exist yet or whose greater part changes. The rule ships to every consumer project through the CLAUDE.md pointer block `/setup` writes (§ *Edits are surgical*), and Workflow 2 step 4 restates it; the editor's "a finding that names a line is an edit, not a dispatch" (8.31.1) is the same rule at the orchestration level.

**Measuring a run**: `scripts/session-cost.ts` reads the transcript Claude Code writes under `~/.claude/projects/<cwd-slug>/*.jsonl` and reports what the run paid (input + cache write + output), what the model attended to (context re-sent every turn — `avg context/turn` against a 40K target), the main-session / sidechain split (the delegation ratio), per-model turns, tool counts, every path `Read` more than once (the payload should have carried it) and the most expensive turns. **One API call is one turn**: Claude Code writes a response as several records sharing a `requestId` with the same `usage`, so summing records double-counts. The orchestrator cannot measure its own context, so a run to be measured goes in a fresh session and is read afterwards. **A run that is meant to measure delegation must ask for it**: a session policy that suppresses sub-agents unless the user requests them makes the skill take its in-session route: Workflow 1 Step 5 asks before falling back, the final report carries `route: delegated | in-session`, and the measurement prompt says "usa sub-agentes" explicitly.

## Generic by Construction — a project is evidence, never the spec

The skills create architectures — any architecture, in any domain, organization and language the plugin supports. A consumer project is where a defect is **observed**; it is never what the fix is **written for**. Before changing the plugin from something seen in a project:

1. **State the defect as a rule about every architecture.** "This service lost its OpenAPI" is the observation; "an HTTPS/JSON inbound edge is a REST surface" is the rule. If the rule cannot be stated without the project's names, the fix is not ready.
2. **Read the fact from the project's own documents at run time** — the ledger, docs/05, the descriptors — never from a list, a name or a threshold copied out of the project. A vocabulary that belongs to one domain (a bank's nouns, one team's naming scheme) is the judge's question (`scripts/judge.js`), not a constant in the plugin.
3. **Tests and examples are synthetic.** A fixture invents its components (`Order Desk`, `Hub API`); it never reuses a project's canonical names, slugs, internal names or ids. Examples built from real data are never committed.
4. **Comments and instructions state the general case.** "Another component's name in the deployment section", not that component's name. Where a rule was measured belongs in `CHANGELOG.md` and `docs/DESIGN_NOTES.md`, and even there by its shape (counts, dates), not by quoting the project.
5. **Fix the project's own defects in the project.** A document that is wrong is an edit of that architecture, never a special case in the plugin.

**The control is code**: `bun scripts/check-generic.ts` (in `bun run check`) reads the maintainer's reference projects — one path per line in the untracked `.sa-reference-projects`, or `SA_REFERENCE_PROJECTS` — takes each one's own names from its facts ledger (component canonical names, slugs, internal names, system names, the folder name; never a technology) and fails on any that appears under `scripts/`, `skills/`, `agents/`, `plugins/`, `hooks/`, `tools/` or `commands/` outside `scripts/generic-baseline.json`. `scripts/generic-baseline.json` — a hash per (file, name), naming no project — is **empty** and stays empty: a new hit is fixed, never baselined. With no reference project configured the check is skipped. A name is the part of project-specific drift code can see; rules 1, 2 and 5 are the reviewer's.

## Compliance is isolated

Compliance is not in the base: the contracts, their questions and the ADR coverage map ship with an organization's institution pack (10.0.0). No skill, agent or script of the base reads what a compliance plugin writes — `compliance-docs/`, the `CC-NNN` contracts, `COMPLIANCE_MANIFEST.md`, requirement codes — except the **command center** (Alia's dossier, for visualization), which shows them when they are there. Analysis, the dev-handoff kit, docs-export, the component guardian, architecture-docs' checks, claim-sweep and sa-ux's radar read nothing of compliance; `plugins/sa-analysis/skills/architecture-analysis/tests/independence.test.ts` and `plugins/sa-delivery/skills/architecture-dev-handoff/tests/independence.test.ts` hold the two largest to it. A line that only routes a request ("for compliance contracts, use the compliance skill an institution pack installs") is allowed. The ADR skill carries a catalog's `COVERAGE_MAP.json` as data — imported with the catalog, diffed on sync — and never derives it.

## Code Architecture

**Skills**: Each skill is a directory (`skills/<name>/` in sa-skills, `plugins/<plugin>/skills/<name>/` in the others) holding a `SKILL.md` frontmatter file, its Markdown guides, templates and JSON schemas, and the Bun code its steps run (`scripts/*.js`, `utils/*.ts`) — the deterministic work lives there, not in the Markdown. `architecture-analysis` ships the findings contract (`scripts/findings.js`, the parser; `scripts/check-report.js`, the check every report passes before the skill accepts it); `architecture-command-center` ships a zero-dependency renderer (`scripts/render.js`) plus the Three.js `VIEWER_TEMPLATE.html` it fills, and its `dossier.js` requires the analysis skill's contract module.


**Component facts parser** — `scripts/shared/component-facts.ts` (re-exported from `skills/architecture-component-guardian/utils/component-facts.ts`), CLI `component-cli.ts`. The **single sanctioned reader** of the component tuple (canonical name, C4 type, technology, slug). Subcommands: `list` (JSON `ComponentFact[]`), `index` (the 5-column README table body), `check` (exit 1 on drift or authoring defects). Consumers — diagram generation (guide + Workflow 8), the Workflow 1 completeness check, design-driver counts, IcePanel sync, dev-handoff, the six analysis specs, `architecture-docs-export`, and the analysis and docs-export agents — call the CLI instead of re-parsing `docs/components/**/*.md` or the index; every call site falls back to the README when `bun` is unavailable. Reuses `listDocFiles` / `parseHeader` / `extractH1` from `skills/architecture-explorer-headers/utils/header-detector.ts`. A descriptor typed as a System (`**Type:** External System`) is L1 wherever it sits, and the rows of an L1 descriptor's `## Containers` table (`Component | Type | Technology [| Internal Name]`) are emitted as L2 facts with `file_backed: false` — owned by that system, resolvable by name, type and technology; consumers that need a file per component (the index, the handoff kit, the header check) filter on `file_backed`. **The tagline is a contract**: every file-backed L2 container carries `**Description:**`, one line that opens with the canonical name (the H1 verbatim, plain text) and runs 120 characters at most, name included — the fixed-width slot the index, the briefing tables and the command center print beside the name; the parser reads it as `description` (also on the facts ledger), `checkDescription` is the rule, and `check` reports `missing-field: **Description:**`, `description-name-prefix` and `description-too-long`, each an edit at that line, never a re-dispatch. Tests: `skills/architecture-component-guardian/tests/component-facts.test.ts`.

**Agents vs. Skills**: `agents/` holds sub-agents spawned by skills via the Agent tool. They are **not** skills and NEVER to be invoked directly from user-facing prompts.

**Analysis pipeline (payload, fill, renderer)**: the lens agents never explore the corpus or type a report. `plugins/sa-analysis/skills/architecture-analysis/scripts/analysis-prepare.js <project> --lens a,b|all` cuts one payload per lens — the **plan** (`analyses/plans/<lens>.json`: every section in order with its anchor, titles in both languages, columns as the spec spells them, id regex, heat-map axes, charts), the spec's classification rules, the ledger facts with canonical names, the **computed** metrics (the dependency graph from docs/05 rows and the descriptors' link-text Depends on / Consumed by lines — fan-in, fan-out, instability, direct and transitive dependents, cycles; the sum of each flow's phase budgets against its target; the deployment inventory and `simulation.js` load model from the newest scene; the technologies grouped by a built-in vendor registry, flagged as a guess), what earlier reports registered on each component, and the explorer excerpts (the vocabulary lives in the script) — plus a documents bundle (ARCHITECTURE.md and the plan's prose docs, whole), both written in parts of at most 38 KB that one Read returns whole (Read's 25,000-token limit), listed in order on part 1's reading list; a spec that refers to the Design Language Standard gets its mode and §6 extract in the payload, from the edition of `doc_language`. The agent (`tools: Read, Write, Bash, WebSearch`) reads those two files, writes `.cache/sa-skills/analysis/<lens>.fill.json` (rows per section, heat-map cells, blocks, recommendations, verdict, gaps, citations, `viz` only for the two edge-based lenses in HTML mode) and runs `render-analysis.js`, which validates the fill against the plan, renders Markdown or HTML (the d3 `data` literal derived from the rows), joins the SPOF ids into the Blast Radius rows from the SPOF report on disk, and runs `check-report.js` on the result. `security-posture.js` consolidates the checklist from the STRIDE and Data Sensitivity reports with no agent at all. **The direction of a docs/05 row is a judgement, not a lexicon**: `analysis-prepare.js` asks one Choice per row — `call` (From depends on To), `data` (To depends on From), `unclear` — with the row alone as state; the answer and its provider print on every edge (`· jev-1.13.0 0.99`); a row the judge answered `unclear` or below the band is marked `uncertain`, gets no direction, stays out of the graph metrics and is named under **Direction not stated** as a docs/05 gap; a row no judge has answered gets no direction either and is listed as undecided. `--verify <fixtures.json>` measures the answers (`[{ "id": "I-14", "label": "call" }]`); `--judge` overrides the engine per run. `analyses/plans/README.md` is the plan and fill contract; `tests/render-analysis.test.ts` renders every plan from a synthetic fill in both formats and languages. Inventory-heavy lenses run on Sonnet (SKILL.md Step 3).


**Architecture explorer (code)**: `scripts/shared/explorer-cli.ts` (the old path under `skills/architecture-explorer-headers/utils/` still runs it) is the front door to a project's architecture surface (`ARCHITECTURE.md` + `docs/**` + `adr/`). `manifest <project_root>` prints an `EXPLORE_MANIFEST` block — every doc and component file with its `<!-- EXPLORER_HEADER -->` fields, every ADR with status and scope, the document language and its source; `findings <project_root> --query "<terms>" [--surface docs]` prints an `EXPLORE_FINDINGS` block — where each term (a literal, or a pre-built regex alternation when any item carries `|`) appears: file, line, nearest heading, excerpt, per-term coverage with the zero-match stem relaxation, the 10-file / 5-cluster caps with the term-coverage guarantee. Pure module `explorer.ts` (reuses `header-detector.ts`), tests in `explorer.test.ts`. **No ranking, no cache, no model tokens.** Consumers call the CLI from Bash (`architecture-docs`' workflows, `architecture-command-center` Step 1) or require the module (`analysis-prepare.js`, `traceability-prepare.js`, `section-prepare.js`, `dossier.js`).

**EXPLORER_HEADER contract (8.4.0+)**: `header-detector.ts` is the one parser (`parseHeader` reads the closed key set `ALLOWED_FIELDS` and drops any other key silently); `explorer-cli.ts check <project_root> [--file <path>]` is the gate — a header right after the H1, one block, only known keys (a translated or invented key is an error), the required fields, `component_self` equal to the file's slug, `components` and `related_adrs` that exist on disk; warnings for a `scope` over 120 characters or a missing 30-second summary. It runs **blocking** at Workflow 1 Step 5.7 (check 2b), at the Post-Write Audit (Check H) for an edited section or component file, in the guardian and the backfill skill after every header they write, before a command-center scene, and as a release gate (`lifecycle.js check`). `header-contract.test.ts` parses every example header in the guide and the skills against the parser and checks the guide's field guidance against `ALLOWED_FIELDS`, so the documentation and the parser cannot drift without a red `bun test`. `dossier.js` requires the same parser.

**Versioning**: sa-skills, sa-records, sa-requirements, sa-analysis, sa-delivery and sa-visualization move together; the optional **sa-ux** versions itself (`plugins/sa-ux/.claude-plugin/plugin.json`). Canonical version lives in `.claude-plugin/plugin.json` — `marketplace.json`, `package.json`, `CHANGELOG.md` and the README badge track it, and `scripts/build-release.sh` reads it rather than hardcoding one.

**Commits** follow scoped Conventional Commits: `<type>(<scope>): <description>`, with `!` after the scope for a breaking change. A commit that ships a release appends the version — `feat(component-guardian): one tested parser for the component tuple v5.2.0`. Commits that do not move the version (`docs:`, `chore:`, `refactor:`) carry **no** version suffix. The `/release` skill bumps, commits, and pushes.

**Document export**: `tools/docgen/generate-doc.js` renders Markdown to **Word (.docx) or PDF**. The
CLI is flag-based:

```bash
bun run tools/docgen/generate-doc.js --type <type> --input <file.md> --output <file> [--format docx|pdf] [--lang en|es] [--mermaid auto|on|off]
```

`--type` is one of `solution-architecture`, `adr`, `handoff`, `po-spec`. `--format` defaults to `docx`. Optional metadata flags: `--title`, `--author`,
`--version`, `--status`, `--score`, `--approval-authority`.

Both formats share the Markdown parse layer (`extractDirectives` → `parseMarkdown` → blocks); only
the block→document stage differs. The PDF renderer is `tools/docgen/render-pdf.js` (pdfmake), and
it is `require`d lazily so an install carrying only `docx` keeps a fully working Word path.
Unit tests: `tools/docgen/render-pdf.test.js`.

**PDF fonts**: Roboto is embedded from pdfmake's own base64 `vfs_fonts` — no vendored `.ttf` and no
system-font dependency. Roboto covers Latin-1 and General Punctuation in full (Spanish accents,
`¿¡`, em/en dashes, `·`, `…`, `•`, curly quotes, `€`) but **not** arrows, dingbats, box drawing or
emoji, and pdfkit silently drops what a font cannot map. `render-pdf.js` therefore transliterates
those to ASCII (`→` → `->`, `✓` → `[x]`, `⛔` → `[STOP]`) before rendering. Extend `GLYPH_MAP` there
rather than letting a character vanish.

**Mermaid diagrams render as pictures.** `render-mermaid.js` runs between `parseMarkdown` and either
renderer, replacing each ````mermaid``` `code` block with an `image` block that both renderers place —
centred, fitted to the text column, at the size Mermaid laid the diagram out for. It shells out to
**mermaid-cli (`mmdc`), an `optionalDependency` of `tools/docgen`** (a stakeholder reading
`flowchart TB` source in Courier New reads nothing). `bun install` at the repo root puts
the shim in `node_modules/.bin`, where the binary is auto-detected — as it also is from `MMDC_PATH`,
from any `node_modules/.bin` at or above `tools/docgen/`, or from `PATH`. Optional, not plain: a
machine that cannot build Puppeteer must still get a working Word path. **Bun does not run Puppeteer's
post-install browser download**, so the browser is the remaining piece —
`bunx puppeteer browsers install chrome`, or `PUPPETEER_EXECUTABLE_PATH` / `--mermaid-puppeteer-config`
pointing at one already present. `bun scripts/setup-docgen.ts` reports the whole chain (`docx`,
`pdfmake`, `mmdc`, browser) and, for each piece missing, what breaks and the command that fixes it; the
browser line is a **real render of a throwaway diagram**, because an `mmdc` that resolves and cannot
reach a browser passes a presence check and fails on the first export. `/setup` runs it at Step 7,
as a report and never a gate (`--strict` makes it one for CI; `--no-smoke` skips the render).

Every degraded path keeps the diagram: no mermaid-cli, `--mermaid off`, a diagram that will not parse,
or a cache file that vanished mid-run all fall back to the diagram's source in Courier New,
and the run still succeeds. `--mermaid on` is the opt-in that turns a missing
mermaid-cli into an error. `--mermaid-scale` changes resolution only, never layout: the pass divides
the device pixels back out, so the picture lands at its CSS size at *scale* × the dots per inch.
PNGs are cached by a hash of the source plus every option that changes the pixels, under
`${TMPDIR}/sa-docgen/mermaid` (override with `SA_DOCGEN_MERMAID_CACHE`), so re-exporting an unchanged
architecture launches no browser at all. Unit tests: `tools/docgen/render-mermaid.test.js`.

**npm packages load pinned** (8.129.1): every `require` of an npm package goes through `scripts/shared/pinned.js` (`pinnedRequire(root, spec, { installIn })`) — the package must be on disk under `<root>/node_modules`, inside the range `<root>/package.json` pins, or it is refused with the `bun install` command. Claude Code's plugin install runs no `bun install`, and with no `node_modules` Bun auto-installs on first use at the latest version whatever the pin (an installed 8.129.0 got graphql 17.0.2 against `^16.14.2`); a shipped `bunfig.toml` cannot stop it, since Bun reads that file from the working directory, the user's project. docgen (`docx`, `pdfmake`), the contract checks (through sa-delivery's `requireFromSaSkills`) and both `/setup` checks (`setup-docgen.ts`, `setup-contracts.ts`, which print `<version> installed, pinned <range>` for an off-pin package) use it. Tests: `scripts/pinned.test.ts`.

`tools/docgen/` is a **workspace member**, not a separate install: root `package.json` declares
`"workspaces": ["tools/docgen"]`, and `tools/docgen/node_modules/{docx,pdfmake}` are symlinks into
the shared `node_modules/.bun/` store. Run **`bun install` from the repo root** — a
`cd tools/docgen && bun install` is not the documented path and is not needed. `pdfmake` is an
`optionalDependency`: `generate-doc.js` requires `render-pdf.js` lazily inside the
`format === 'pdf'` branch, so an install carrying only `docx` keeps a fully working Word path and
fails with an actionable message only when `--format pdf` is requested. Runtime is **Bun only**;
`node` is not an authorized runtime.

## Architecture Documentation Rules

Detailed per-skill documentation lives in each `skills/<skill-name>/SKILL.md` — consult those when invoking a skill. This section captures only the cross-cutting rules Claude must honor while operating in this repo.

### Quick Reference
- All architecture documents must be named `ARCHITECTURE.md`
- Primary template: `ARCHITECTURE_DOCUMENTATION_GUIDE.md` (inside `skills/architecture-docs/`)
- ADR template and guide: `plugins/sa-records/skills/architecture-definition-record/` (the ADR skill ships in the `sa-records` plugin, a dependency of `sa-skills`)
- Every `ARCHITECTURE.md` carries a semantic version (see "Architecture Versioning" below)

### Four-Phase Workflow
1. **Business Requirements** (PO) → `architecture-readiness` → PO Spec
   - **1.5 Capability Alignment Gate** (Architecture Governance) → `architecture-capability-alignment` → the declared framework's report (`BIAN_ALIGNMENT.md` for BIAN, `CAPABILITY_ALIGNMENT.md` otherwise) — mandatory before Phase 2 Workflow 1 once a framework is declared
2. **Technical Architecture** (Architecture Team) → `architecture-docs` → ARCHITECTURE.md
3. **Compliance Documentation** (Compliance Team) → the compliance plugin an institution pack installs, when the organization has one
4. **Development Handoff** (Dev Team) → `architecture-dev-handoff` → per-component handoffs + assets
   - **Architecture Index** (CI, after each release) → `architecture-index-export` → the `sa-index/1` bundle an MCP server serves to developers' IDEs: search at the tag, build packs once the regenerated kit is committed

**Documentation Language Gate (Phase 2, Step 0.1)**: The **first** gate of Workflow 1, ahead of the PO Spec gate. The architect selects `en` or `es`; the answer is stamped as `<!-- DOC_LANGUAGE: xx -->` in `ARCHITECTURE.md` and governs the authored language of every artifact produced downstream in Phases 2–4. No skip override. Re-runs resolve silently from the marker. See "Documentation Language (EN / ES)" below.

**PO Spec Gate (Phase 2)**: When no PO Spec exists, the user chooses: (1) full `/skill architecture-readiness` elicitation, (2) async intake from a file, (3) provide context inline (scored against rubric with gap interviews), or (4) skip with `SKIP PO SPEC`. Applies only to new document creation, not editing.

**Capability Alignment Gate (Phase 1.5)**: BIAN is banking's reference model, not every industry's, so the gate aligns the PO Spec to the **capability framework the project declares** — `.sa-skills/project.json` (`frameworks.js --declare <id|none>`), else an institution pack's `defaults.framework`, else an existing `BIAN_ALIGNMENT.md` / `ENTERPRISE_ALIGNMENT.md` (BIAN), else Workflow 1 Step 0.3 asks once. `gates-check.js` reports it on the `0.3 align` line: declared `none` passes and `docs/01` § 1.5 is omitted; a declared framework requires its report — no skip override; it cascades-skips only when the PO Spec gate was skipped. The architect runs `/sa-requirements:architecture-capability-alignment [--framework <id>]`; the Summary, the impacted domains and units — and, for BIAN, the Diagram ID Segments and the API Surface — are lifted into `docs/01-system-overview.md` § 1.5 (`BIAN Capability Alignment` for BIAN, `Capability Alignment` otherwise), with the `BIAN_ALIGNMENT_GATE` / `ALIGNMENT_GATE` markers `collect-save.js --framework --alignment` records. A pre-v6.0.0 `ENTERPRISE_ALIGNMENT.md`, or a BIAN report below `BIAN_ALIGNMENT_VERSION: 3.0`, blocks with a regeneration message rather than being rendered.

### Architecture Versioning

Every architecture carries a **semantic version** (MAJOR.MINOR.PATCH) — the canonical reference for all downstream artifacts.

**Whole-architecture version** (in `ARCHITECTURE.md` header):
```markdown
<!-- ARCHITECTURE_VERSION: 1.2.0 -->
<!-- ARCHITECTURE_STATUS: Released -->
<!-- ARCHITECTURE_RELEASED: 2026-04-08 -->

**Version**: 1.2.0
**Status**: Draft | Released | Deprecated
**Released**: YYYY-MM-DD
**Architect**: [Name or Team]
**Supersedes**: v1.1.0
```

**Per-component version** (in each `docs/components/**/*.md`, after the C4 metadata block):
```markdown
**Component Version:** 1.3.0
**Architecture Version:** 1.2.0
**Last Updated:** 2026-04-08
```

**Semver rules** (recommended by code, `lifecycle.js` BUMP_RULES; the user confirms):
- **MAJOR**: something a consumer relied on is gone or the structure changed — a system added or removed, a container, integration, flow or section removed, the architecture type changed
- **MINOR**: something added or a decision moved — a container, ADR, TDR, integration, flow, phase, layer or section added; a container's name, type or technology; an integration's route; a flow's phases; an ADR's status
- **PATCH**: the text changed and the structure did not

**Lifecycle**: `v1.0.0` Draft → first release (Status: Released + git tag `architecture-v1.0.0`) → bump per semver on each change. All released versions recorded in `docs/CHANGELOG.md` (Keep a Changelog format).

**Git tag**: `architecture-v{version}` — namespaced to distinguish from plugin/app tags. MUST reflect the doc version under git.

**No archive snapshots** (8.139.0): the tag is the only baseline — a release needs git, and a correction is a new PATCH release.

**Downstream reference**: Compliance contracts, handoffs, and traceability reports include `Architecture Version: v{version}` in metadata for baseline traceability.

### ADR Scope Partition
- **ADR-001 … ADR-100** — **Institutional** (org-wide Architecture Team decisions)
- **ADR-101+** — **User / Project** (local to a single project)

Institutional range is hard-capped at 100; overflow blocks until an existing institutional ADR is superseded or the new decision is reclassified.

**Institutional ADRs live in the project.** When an organization keeps its institutional catalog outside the project, it is imported into `adr/` by `architecture-definition-record` Workflow 6 — never referenced by absolute path. Citations must resolve on disk: ID assignment, Layer 2 principle review, compliance validation and traceability all read `adr/*.md`, and a catalog they cannot open degrades each of them silently. Imported ADRs are copies and do not track the source catalog; re-run the import after a catalog update and never hand-edit an imported institutional ADR locally.

### Component Index Policy
`docs/components/README.md` is writable **only** by `architecture-component-guardian`, which enforces the fixed 5-column schema (`#`, `Component`, `File`, `Type`, `Technology`) with grouped system headers for multi-system architectures. Redirect direct-edit requests there.

**The component file is the source of truth; the index is derived from it.** `docs/components/**/*.md` holds the authoritative `**Type:**`, `**Technology:**` and H1; the README is regenerated from those files and can be stale between guardian `sync` runs. No skill may hand-parse either one — read the tuple through `component-cli.ts` (see "Component facts parser" above), which reads the files and reports index drift as a finding.

### Component Naming Fidelity
When generating any user-visible artifact that references a documented component by name (analysis reports, dev handoffs, `.docx` exports, traceability reports, prose summaries, diagrams), use the **canonical full name** exactly as the component file's H1 gives it — `name` from `component-cli.ts list`. Do **not** abbreviate, truncate, or alias even when source `docs/**/*.md` files use a shortened form inline — source-doc shortening is for inline readability, not for downstream propagation. Example: write `shp-bs-gift-cards-and-bundles` every time — never `omn-bs` or `gift-cards-and-bundles` standalone. The 10 agent files under `agents/**/*.md` and `plugins/*/agents/**/*.md` that write about the architecture (all but `worksheet-judge`, which judges a worksheet's items, and `acceptance-test-writer`, which writes tests from a PO Spec — neither names a component) each carry a `## Component Naming Fidelity` block enforcing this rule at the agent level; the analysis and handoff templates carry it as authoring-time guidance. The block comes in two variants, matched to the agent's declared tools: the agent holding `Bash` for that purpose (`docs-export-generator`) resolves names by running `component-cli.ts list`; the others read the component file's H1 directly with `Read`, or use the canonical name the orchestrator already resolved and passed in (`architecture-analysis-agent` holds Bash only for the render command and takes the names from its payload's Components table, 8.50.0). This rule is **complementary** to the Asset Fidelity Rule and "no invention" policy below — those bind structured asset values; this binds component-name occurrences in prose, tables, diagrams, and citations.

**Internal name**: a container may also carry an `**Internal Name:**` metadata row (the repository / workload / product identifier, e.g. `shp-spa-order-history`; `internal_name` from `component-cli.ts list`, `internal_name` in its `EXPLORER_HEADER`). For a container an external system declares only as a row of its descriptor's `## Containers` table, the identifier goes in that table's **`Internal Name`** column (8.20.2) — prose is not read. It is a **second identifier shown beside the canonical name**, never a substitute for it: write `MFA Historial de Pedidos (shp-spa-order-history)` where both help, and never the internal name alone in prose.

**Source precedence**: the component file's H1 is authoritative. `docs/components/README.md` Column 2 is a **derived** copy that can lag the files until the next guardian `sync`, and the `ARCHITECTURE.md` Component Index is the last fallback. When the index and the file disagree, the file wins — report the mismatch as index drift rather than propagating the stale name. All 10 agent blocks carry this precedence rule verbatim as a `**Where the canonical name comes from**` paragraph.

**Step 0.1** — the first gate, ahead of the PO Spec gate. Supported values: `en`, `es`.

### Prose Style (generated documentation)

Documentation the plugin writes into a user's project is **minimal prose, direct, technical**.
Skill and agent files in this repo are instructional and are not bound by this — the contract
governs output, not instructions.

**Form ladder** — pick the first form that fits: a table for ≥2 items with ≥2 attributes; bullets
or `**Label**: value.` triplets for ≥2 items with one attribute; a Mermaid diagram for interactions
and structure; a single `**Label**: value.` line for one labelled fact. **Prose is the fallback,
never the default**, and is allowed only in a closed list of designated slots (mission statement,
Problem Statement, Solution, 30-second summary, per-UC delta, out-of-domain clause, ADR
Context/Rationale/Consequences, TDR Impact, principle Description).

**Never**: template boilerplate that leaked into a deliverable ("This section provides a visual
representation…"), filler openers, meta-narration about the document's own layout, hedges,
marketing register, first/second person in `docs/**`, or **mannered prose** — metaphor and flourish
where a literal phrase exists (*a dial worth turning* for *a parameter worth varying*; `PROSE_STYLE.md`
§4.5, from Anthropic's Fable 5.1 prompting guide § Writing density, carried by every agent's Prose Style block). Present tense, active voice, third person
about the system. Both language branches are normative — Spanish adds impersonal `se` and pro-drop
first person (`aprovechamos`), which a pronoun-only check misses.

**No file-length cap.** The contract caps sentences (≤25 words) and paragraphs (≤70 words), and
those are WARNINGs. It never counts lines in a file. The `~400` / `~130` line figures that used to
appear in `RESTRUCTURING_GUIDE.md` were stale and have been removed — do not reintroduce them.
Split, never delete: dropping a fact to satisfy a length finding is a defect, not compliance.

**Enforcement** is three-tier. `ARCHITECTURE.md` + `docs/**` are gate-enforced by
`PROSE_VALIDATION.md` (Step 5.7 Content Hygiene Gate check 3, Post-Write Check F, the release check
release scope) — 5 BLOCKING lexical rules, 8 WARNING judgement rules (`S-DENSITY-02` is mannered prose).
**And at the moment of writing**: the plugin's `PreToolUse` / `PostToolUse` hooks on `Write | Edit`
(`hooks/prose-hook.sh` → `skills/architecture-docs/scripts/prose-hook.js`) run `prose-check.js` on the **new lines** of a
call to `ARCHITECTURE.md`, `docs/**`, a project ADR or a TDR — before: a BLOCKING lexical rule denies the call under an
enforcing project, with the rule and its fix; after: the length and form warnings come back as context in the same turn.
Judgement rules stay with the gates (no judge, no network in a hook, ~100 ms). Why: without it a first write
comes back with hundreds of warnings fixed pass after pass, and an edit never sees the length rules.
**The rulebook is code**: `skills/architecture-docs/scripts/prose-check.js <project> [--scope] [--file …] [--judge] [--deep] [--json] [--warn-only]`
runs every rule — the blocklists as the regexes the rulebook prints (both branches always), the mechanical warnings by count,
the proper-noun guard from the ledger — and hands the judgement rules to `scripts/judge.js`, one Noul per regex candidate
(`S-VOICE-01` pro-drop verb, `S-VOICE-02`, `S-VOICE-03`, `S-DENSITY-01`, `S-DENSITY-02`; `--deep` reads every paragraph for
mannered prose); a candidate no judge has answered is reported as undecided, never kept, and every dismissal prints with its probability.
**The four workflows call the script**: Step 5.7 check 3 (`--scope first-write`),
Post-Write Check F (`--scope edit --file`), the release check (`--scope release`, blocking, the waiver reason carried into the
release notes) and Workflow 12 / `/restyle-architecture` (`--scope release`, with the judge where a key is set); the scope map of
Appendix A is code in the script (`SCOPES` / `GROUP_OF` — `edit` runs Groups 1, 2, 6 and 8, `release` enforces whatever the marker says,
`PROSE_STYLE_WAIVED` exempts it and prints). ADRs, TDRs, handoffs,
analysis and alignment carry the contract without a gate.
`S-VOICE-01` runs the pronouns of `DOC_LANGUAGE` only, case-sensitively, outside code spans and quoted text, and code
dismisses accented `-amos` nouns (`préstamos`, `últimos`), since a case-blind bilingual list blocks
`East US` and `us-east-1`; a changelog is checked in its `[Unreleased]` block only and never for length; a multi-line
comment (an `EXPLORER_HEADER`) is not prose; **Group 8 — history** adds `S-HIST-01` dated narration (judged; weak
markers such as "desde el" count only beside a date or an amendment) and `S-HIST-02` edit-marker comments
(`<!-- corregido … -->`, BLOCKING); `S-FORM-01` counts a section's subsection tables; an identifier (`I-04`) is a
density token. Workflow 12 applies size budgets **before** splits, may delete a fact only where `fact-locate.js` finds
it at the kept link ("never drop a fact from the corpus"), and reviews every section with `qualifier-check.js`
(a dropped `Proposed`, `no verificado`, severity, unmeasured threshold or cost against the baseline) and `superseded-claims.js` (retired ADR wording still asserted — a shortlist, not a
gate) before stamping; a restyle is update intent under the confirm-first rule, its change set the `--dry-run` report.
`flow-check.js` flags prose after the phase list on a `**Phases**:` line (`phases-prose`). **ADRs and TDRs are held to
the same standard**: per-section word budgets (ADR Context 250 · Decision 500 · Rationale 250 · Consequences 300 · Alternatives 250,
body ≤ 1,500; TDR Description 200 · Impact 150 · Solutions 150, body ≤ 600) and one line per log entry, in `docs-stats.js`
(`tdr-check.js` requires the same function) and `prose-check.js --scope records` (logs skipped) — BLOCKING once stamped; their **structure is English with no anchor comment** (`LANGUAGE_POLICY.md` §4 *Records*, one vocabulary in `record-structure.js`: `S-STRUCT-01` for a project ADR, `structure-localized` in `tdr-check.js`); the ADR
template's Rationale and Consequences are one-line bullets and Alternatives one table; `architecture-definition-record`

No gate scores prose quality beyond the lexical rules — register drift, form choice, whether a

render calls `generate-doc.js` directly rather than spawning `docs-export-generator` — a single
deterministic render with no composition step, already covered by `Bash(bun *)`.

The filename stays English under `DOC_LANGUAGE: es` (filenames are on the do-not-localize registry);
only the document chrome localizes. No new permission is required — `Bash(bun *)` and
`Write(exports/*)` are already granted.

### Dev Handoff Scope
`architecture-dev-handoff` is scoped to **C4 Level 2 (Container) components only**. C4 Level 1 (System) descriptors are excluded — they describe system boundaries, not implementable units.

### Diagram Policy (architecture-docs Workflow 8)
4 standard diagrams always generated — Logical View (`flowchart TB`), C4 L1 System Context (`C4Context`), C4 L2 Container (`C4Container`), Detailed View (`graph TB`) — plus Data Flow sequence diagrams per documented flow. **All four are Mermaid.** The Logical View uses `subgraph` bands with edges between band ids (the one place subgraph-level edges are required rather than forbidden), and **replaces** — never supplements — an ASCII block found in an older architecture. **Diagrams 1 and 4 share one fixed four-role palette** — `zone` (band, `fill:none`) / `unit` / `store` / `ext`, assigned by drawing role on every architecture type, with **no dark-theme variant** and no per-type layer-role palettes (channel blue, business green, core red, messaging purple, and their dark variants must not survive a regeneration). Theme detection governs only Diagrams 2, 3 and the sequence diagrams — and only in fallback mode; governed mode has none (the §9 palette directive replaces it). **The theme is never asked**: governed mode reads and writes no `DIAGRAM_THEME`; fallback mode honours an existing marker and otherwise defaults to light silently — the standard defines one palette, so the question had no useful answer. `.docx` and `.pdf` export renders every Mermaid diagram — the Logical View included — as a picture, via `tools/docgen/render-mermaid.js` and an optional, auto-detected mermaid-cli; without mermaid-cli the export falls back to source. All Mermaid targets **v11.4.1**. Canonical locations: standard diagrams in `docs/03-architecture-layers.md`; Data Flow in `docs/04-data-flow-patterns.md` (not configurable). **Workflow 1 Step 7.1 writes the four from one payload**: `skills/architecture-docs/scripts/diagram-prepare.js <project>` → `.cache/sa-skills/payloads/diagrams.md` — the Step 7.1 requirements and the 7.3 audit, the generation guide's sections for the four diagrams (not the 18 KB Connection Naming Rule; governed mode drops the C4 colour and theme sections), the design standard's skeleton, canonical palette block and self-check in the document's language, the `label-check.js` registry, the facts, the Mermaid HLD, `docs/03`'s outline and the check commands; the guides, the standard, the documents and the scripts' source are not read. With automatic checkpoints it goes to a `segment-runner` (`items: diagrams`), never a general-purpose sub-agent (which reads the guides and the standard whole). Architecture docs are authoritative — diagrams for undocumented flows are discarded. **`§ End-to-End Wire Sequences` of `docs/04` is derived, never drawn**: `skills/architecture-docs/scripts/flow-compose.js <project>` writes it from the Phase Catalog panels each flow's `**Phases**:` line declares — participants unioned by display name (`DGACP` and `DR` are one lifeline), every numbered step relabelled `N.M` (phase N, the panel's own step M — one numbering across every flow, the phase's own; a non-monotonic run is information), the §9 directive once, a hand-authored sequence **kept** where nothing derives; `--check` is the drift gate (Workflow 8 Step 7, the release check). **Every write of `docs/04` then ends with `flow-check.js <project>`**: `docs/04` states every flow twice — the phases its block names, and the complete sequence — and the check holds the two to each other. Findings: `phase-absent` (a declared phase the sequence does not contain; both readings are live and the finding names neither), `sequence-missing`, `flow-block-missing` (the inventory lists a flow the ledger cannot pair by name — everything downstream then prints `Not documented`), `phases-undeclared` (the composition written as prose instead of the `**Phases**:` line the ledger reads). Warnings: `phase-hops-missing`, `phase-undrawn`, `phase-orphan`, `sequence-declared-absent`. Heading levels are read from the document, never pinned — projects put the Phase Catalog at H2 or H3, and a pinned level silently empties every flow. A `docs/04` predating the Flow Inventory / Phase Catalog layout is **skipped, never passed**. Run at Workflow 8 Step 7, and before a handoff kit. **Every diagram write ends with `skills/architecture-docs/scripts/mermaid-check.js <file.md>`**: the guide's Pre-Write checklist as code (a `;` inside a message, Note, label or C4 string; HTML tags; emoji; a `|` in node text; odd quotes; on Diagrams 1 / 4 the retired palette, unclassed elements, subgraph-id or node-to-node edges) plus a render through mermaid-cli when it is installed — a block that fails there would export as source, not as a picture. Workflow 8, Workflow 1 Step 7, the guardian and the export's Step A.3a run it. **`docs/05` is held to its sources by `skills/architecture-docs/scripts/integration-check.js <project>`**: every `I-nn` Protocol cell against the §5.3–§5.4 grammar `label-check.js` parses (BLOCKING in governed mode — the diagrams are drawn from these cells), and every edge of a Mermaid HLD against the inventory (`missing` · `reversed` · `action` · `not-in-hld`, WARNING — the HLD is input and a departure is stated, never silent). It gates Section 7 and opens the Step 7.3 audit; the S7 payload carries the HLD, and the S1 payload the gates' traceability markers.

### Design Language Standard (C4 design language for IcePanel)
An organization's **design language standard** — for the reference organization, the *SA Design Language Standard*, its C4 ↔ CSDM ↔ BIAN design language — **comes with that organization's institution pack** (`docs/INSTITUTION_PACKS.md`; since 9.2.0 the base carries none), as `llms.txt`-convention files for agents to read, plus JSON registries for code to check against — **no script parses the prose** (a prose reader registered the twelve tokens §5.4 only illustrates, and took the check id `C-11` for a STYLE):

```
[design_language_dir]/   (scripts/shared/packs.js --path design-language: the pack's design-language/)
├── README.md              # load contract, precedence, known gaps — read this first
├── llms.txt               # 71 lines — index + currency and refusal contracts
├── llms-rules.txt         # 694 lines — THE RULES DIGEST, load this to generate or validate a view
├── llms-mermaid.txt       # 509 lines — Mermaid syntax contract M-01…M-21 (new at v0.6)
├── llms-full.txt          # 5,791 lines / ~117K tokens — full text, Appendices A–E. NEVER read whole
├── llms-HOWTO.md          # 1,124 lines — companion note, 7-question acceptance test + 2 bonus §5 (informative only)
├── rules-registry.json    # 444 lines — every other closed registry as data (labels, tags, LSC/LVL, checks, the label expression); generated and verified by the standard's _registry.ts. Code reads this
├── bian-registry.json     # 762 lines — the closed DOM / CAP / BIAN-id lookup. Read this for a code
├── bian/                  # 9 files — BIAN Service Landscape v14.0.0 as published. Index first, never all
└── es/                    # the 5 llms-* files, ES-LatAm edition. Load one edition, never both
```

**Standing instruction** (from `llms-HOWTO.md` §4) — applies whenever a task touches Diagram IDs, view display names, connection labels, risk tags, export profiles, or conformance checks:

> Answer only from the files above (the copy in force). Do not answer from general C4, C4-model or IcePanel knowledge, and do not answer from any other copy of this standard. **The version in force is v1.0 (release candidate 6), built 2026-10-16.** Every registry in these files is closed — the Diagram ID segments, the 8 `DOM` codes, the 43 `CAP` codes, the 15 Action Types, the tag-group vocabularies and the export profile names are registries, not conventions. **Never invent a value**; if one is not registered, say it requires a vocabulary extension through the Architecture Governance Board (AGB) and stop. If the answer is not in the bundled files, name the section that would cover it and stop — a partial answer that names its gap is correct; a confident complete answer filled from memory is a defect. Cite the point or section behind every rule you state.

**Load contract**: `llms-rules.txt` (694 lines, ~14K tokens) is the default and is self-contained. Load it on demand only — IcePanel sync, component/C4-descriptor writes, a direct question about the standard, or a **label-check failure** to resolve. **Any write of a connection label** (Workflow 8 diagram generation, a Workflow 2 edit of one edge, a component-guardian regeneration, an ad-hoc "add X to the diagram") ends with `bun skills/architecture-docs/scripts/label-check.js <file.md>` (8.9.0+) — the **Connection Label Check as code**: every label of every `flowchart` / `graph` / C4 block held to the §5.3 grammar and the fifteen §5.4 Action Types, with the registries **read at run time from the bundled `rules-registry.json`** (never transcribed — `--registry` shows what it read, `--expression` the expression it yields, and `tests/label-check.test.ts` holds the guide's printed copy to it), the version stamp on every receipt, `skipped — fallback mode` when the folder is absent. It is the one lexical gate on label vocabulary, since the §10 self-check is syntax-only and `C-11` runs nightly, not pre-write. Never pre-load `llms-rules.txt` for a label write: run the check, read §5 only for a failure. Add `llms-mermaid.txt` when emitting a Mermaid sketch; read `bian-registry.json` to resolve a `DOM` or `CAP` code rather than parsing the digest's §1.3 table. **`llms-full.txt` must never be read whole** — at ~115K tokens it would blow the main-session working set; `rg -n '^## '` for the section offset and read that range only. Escalate to it for Appendix B (per-technology altitude rulings), Appendix C (13 worked modelling cases), Appendix D (authoring runbook), or Appendix E (the normative export catalog). **Appendix F (the RFC and decision log) is named in `llms-full.txt` but shipped separately upstream and is not bundled** — cite the rule, not the RFC. **`bian/` is subject to the same rule**: `bian/llms-bian.txt` (431 lines) is the index; open one area file on demand, never all nine (~120K tokens).

**One edition per agent**: both editions come in the pack. Load exactly one, chosen by the project's `DOC_LANGUAGE` — `es` → `es/`, anything else → the root. **Never load both**: a bilingual context makes the agent quote whichever edition it saw last, and the acceptance test does not catch it. `bian/` and `bian-registry.json` are edition-neutral and load with either.

**Business layer = BIAN as published.** `DOM` is the 8 BIAN Business Areas — `BMG` `RSM` `FRM` `OPS` `PRD` `CUS` `CNL` `BDV`, plus reserved `ENT` — and `CAP` the 43 BIAN Business Domains, mapped 1:1 to the printed BIAN model id. The 341 Service Domains are a tag and a register column, never an ID segment; the grammar stays at six segments. A `CAP` is four letters; a `DOM` and a `LVL` token are three, so length separates the registries. `ENTERPRISE_MODEL.md` is withdrawn and is not a normative source. The Mermaid syntax contract is `llms-mermaid.txt` (`M-01`…`M-21`). The Diagram ID grammar (six hyphenated segments, seven `LVL` tokens) is in the standing-instruction blocks: the register assigns `NNN` only, and the author resolves `LSC`, `DOM`, `CAP`, `SUBJ` and `LVL` from the registries; `llms-rules.txt` §0.1 lists the six identity registries one bullet each, and §1 stays authoritative where the two differ. Red, amber and green are reserved as status colouring, which lives in tags, not as wavelengths; the sketch is the one governed exception to *colour is non-semantic* (`llms-mermaid.txt` §9). **Rejected, do not implement**: a seventh `LEG` Diagram ID segment, a new relationship type, and `XML` in the STYLE registry.

**Acceptance test — run Bonus 2 first.** §5 has **seven** questions and two bonus questions, and the order matters. **Bonus 2 — *list the 43 registered `CAP` codes*** — is the only question in the set answerable from exactly one surface, so it is the one that separates a stale knowledge load from a retrieval failure; run it before diagnosing anything else. **Bonus 1** (the version stamp) proves only that the instruction block was repasted — the stamp lives inside the block, so it passes on a stale knowledge load. `LSC`'s two values (`BP`, `DEU`) sit in Part A, on the principle that the first segment of every Diagram ID must not be contingent on retrieval succeeding.

**Retired vocabulary — must not appear anywhere in this repo**: the 47-capability registry, the `DOM` codes `EMG` / `FRK` / `BEN`, the `CHN` and `COD` codes, and any three-letter `CAP`. The standard's refusal contract uses exactly these as its content test for a stale copy.

**Precedence**: where this standard and a bundled Markdown guide disagree, the standard wins. Its refusal contract explicitly demotes `references/DIAGRAM-GENERATION-GUIDE.md` to **informative only as of v0.3** for connection labels and Action Types (Point 5 §3.4 is the registry of record). `ICEPANEL-C4-MODEL.md`, the 4 standard diagram templates, and the `{TYPE}-TO-C4-TRANSLATION.md` guides are untouched by it and remain governing in their own lanes — except that Appendix B overrides the generic C4 boundary test on specific technologies (an API gateway is Deployment-only, never a C4 L2 container — above Deployment it is the connection's `· Via <name>`, §5.9 since RC5).

**`llms-mermaid.txt` governs the plugin's Mermaid output — conditionally.** When a design language is in force (**governed mode**), `M-01`…`M-21` bind every Mermaid block Workflow 8 writes: Diagrams 2 and 3 are authored as `flowchart TB` views in the standard notation (Mermaid's `C4` type is excluded by the contract), Diagram 4's keyword is `flowchart` never `graph`, every block carries the §9 palette directive pasted verbatim, and theme detection is retired. The data-flow diagrams **stay `sequenceDiagram`** — sanctioned by `M-01`'s named exception for Dynamic views, with `docs/04` recorded as the sequence rendering by design (`B10a`), constrained by §12: numbered business-intent step labels, no protocol/Action Type, no `Note`/`loop`/`alt`/`opt`/`par`/activation/`rect`, no `classDef`. When the folder is absent (**fallback mode**), the prior `C4Context` / `C4Container` / `graph TB` formats apply unchanged. The `#### Diagram:` headings, file locations, ordering and count gates are identical in both modes. Normative section: `DIAGRAM-GENERATION-GUIDE.md` § Design Language Governance. `architecture-icepanel-sync` Step 1.1 carries a governed-notation branch, so the sync does not depend on C4 fences. `MERMAID_DIAGRAMS_GUIDE.md` remains governing for fallback mode and for whatever governed mode does not cover.

**Availability gate**: the standard is organization-specific; this plugin is not. Every consuming skill tests for `llms-rules.txt` first and falls back to its prior behavior when the folder is absent — no skill hard-depends on it. Consumers wired today:

### Permissions
Each skill's required `.claude/settings.json` permissions are documented inside its own `SKILL.md`. A pre-configured example consolidating all skill permissions is at `.claude/settings.json.example` — users installing the plugin copy or merge the `permissions.allow` block into their project settings.

**Plugin limitation**: Claude Code plugin agents do not support `permissionMode` in frontmatter (silently ignored). Permissions must be granted via project settings.

**Reads run on ripgrep** (8.48.0): every search instruction the plugin hands the model is an `rg` command — never `grep -r`, `find -name` or `cat | grep` — and `Bash(rg *)` is in the example permissions and every per-skill snippet. Conversion traps when writing one: in `rg`, `-E` is encoding, `-r` is replace, `-L` follows symlinks and `-h` is help; `--include=` is `-g`; a placeholder such as `ADR-{NNN}` needs `-F` or it parses as a quantifier; `rg -c` prints nothing on zero matches. `/setup` Step 8 runs `scripts/setup-ripgrep.ts` (8.49.0): it reports `rg` on PATH, PCRE2 and the `Bash(rg *)` grant, and writes `env.USE_BUILTIN_RIPGREP = "0"` into the project settings when a system ripgrep exists and neither scope sets the key, so the built-in Grep tool and the skills' searches use the same binary; with no ripgrep it writes nothing and names the install command.

### Optional MCP: context7
`architecture-dev-handoff` and `architecture-docs` optionally use context7 when configured:
